## Objetivo e resultado observável

Com o celular em modo avião: o app instalado na tela inicial abre e mostra a carteira da última sincronização (com data/hora); o vendedor cadastra produtor, propriedade, visita e oportunidade — tudo aparece como "aguardando envio" no indicador do topo. Ao sair do modo avião, a fila envia sozinha, na ordem das dependências, e cada registro existe no servidor **exatamente uma vez**.

**Fila (fila-offline.ts) — contrato:**

```ts
interface ItemFila {
  id_local: string          // UUID v4 gerado no aparelho
  colecao: 'produtores' | 'propriedades' | 'visitas' | 'oportunidades' | 'acoes_oportunidade'
  dados: Record<string, unknown>  // já com id_local dentro
  depende_de?: string       // id_local do pai (propriedade→produtor, oportunidade→visita)
  usuario: string           // RN-25: a fila pertence a quem criou
  empresa: string
  criado_em_aparelho: string
  estado: 'pendente' | 'enviando' | 'precisa_revisao'
  motivo?: string
  tentativas: number
}
```

- **Envio (RN-23):** ordem produtor → propriedade → visita → oportunidade → ação; só envia item cujo pai já tem id do servidor (resolvido em memória durante a sincronização); `id_local` trocado pelo id real nos dependentes.
- **Idempotência:** antes de criar, consulta `id_local = X` no servidor; se já existe e é visível, marca enviado e usa o id do servidor; se 400/404, `precisa_revisao`.
- **Tentativas:** timeout 20 s; espera 5 s → 15 s → 45 s → 2 min → 5 min; esgotadas, volta a `pendente` para o próximo gatilho.
- **Falhas:** 401 mantém a fila e pede login; 403/404 → `precisa_revisao`; 400 → `precisa_revisao` com o motivo do servidor.
- **Cópia de consulta (CA-1-15):** produtores+propriedades da empresa, oportunidades abertas do usuário e linhas de negócio, salvos na store `cache` a cada sincronização; apagada ao trocar de empresa ou sair. A carteira offline lê do cache (a Minha carteira ganha fallback de leitura).
- **RN-25:** toda leitura/envio da fila filtra por `usuario` — outro usuário no aparelho não vê nem envia.

**Regras de acesso:** nenhuma alteração no servidor (a SPEC proíbe). O envio usa o token do usuário dono da fila — as regras das SPECs 1-001 a 1-003 valem no envio.

## Riscos

- **Service worker no Skip:** a SPEC manda parar se a plataforma não permitir — o `public/` é servido estático pelo Vite, então o caminho padrão deve funcionar; se o QA/publicação bloquear `sw.js`, paro e reporto (plano B da SPEC).
- **Modo avião não é testável no navegador do sandbox** — a prova GREEN 1 completa é no celular do Diogo; no sandbox provo a fila forçando `navigator.onLine = false` via contexto e as rotas de falha por API.
- **Áudio offline:** fora de escopo (fase 2) — o botão de áudio fica desabilitado offline com aviso.
- **Dados:** nenhuma migration; nada no servidor muda.

## Roteiro de verificação automática

1. RED 1: 2 POSTs mesma visita com mesmo id_local → 2º 400.
2. GREEN (sandbox): fila em memória/IndexedDB do navegador — enfileirar 3 itens offline simulados, sincronizar, conferir 3 registros no servidor 1x cada; cortar no meio (derrubar rede) e reconectar → sem duplicata.
3. RN-21/24/25: edição offline bloqueada; sair com pendências pede confirmação; fila do usuário A invisível para B (API + navegador).
